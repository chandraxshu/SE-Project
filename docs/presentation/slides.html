Phase 1: Problem Definition

Problem Statement & Motivation

Why traditional ad-hoc lost and found mechanisms fail in university campuses

Channel Architectural Vulnerability Impact on Campus
WhatsApp Batches Messages drown under chat flood within 2 hours; unsearchable Low recovery rates (< 25%); endless duplicate forwards
Institute Emails Inbox clutter; flagged as spam; lack photo preview Information fatigue; missed notifications
Physical Noticeboards Pinned to one wall (e.g. CC3/SAC); weather-damaged Zero reach to students in other hostels or departments
Informal Desk Handover No ID check; zero chain-of-custody tracking Fraudulent claims; dispute liability falls on guards

⚠️ No Identity Verification

Anyone can message a founder and claim an expensive gadget without proof.

🔒 Privacy Exposure

Students publicly blast their WhatsApp and phone numbers to hundreds of peers.

📜 Zero Audit Trail

Once an item is handed over informally, there is zero record of who took it.

Phase 1: Objectives & Scope

Project Vision & Core Objectives

A zero-cost, dispute-proof asset recovery ecosystem engineered for IIIT Allahabad

1. Institutional Security Boundary

Restricted strictly to verified @iiita.ac.in Google accounts. Non-campus users are completely locked out at both frontend and database layers.

2. Anti-Fraud Claim Protocol

Two-factor ownership verification: finder enters secret distinguishing details (hidden from public); claimant must provide proof (receipts, serial numbers) to admin.

3. Security Desk Handover Governance

Physical handover at CC3/Hostel desks requires physical ID card inspection. Admin logs the verified student Roll Number in an immutable audit trail.

4. Omnichannel Mobile Reporting

Telegram Bot (@iiita_khoj_bot) enables students on the move to report lost or found items in 30 seconds with photos without opening a browser.

Zero-Cost Architecture: Vercel CDN ($0) + Supabase PostgreSQL ($0) + Telegram Bot API ($0) = Total Cost: $0.00 / month

Phase 3: Database Design

PostgreSQL Database Schema

Normalized relational schema with cascading constraints and stored procedures

Core Relational Tables

  • profiles: ID, email, full_name, roll_number, department, role, telegram_chat_id.
  • items: ID, title, category, report_type (lost/found), location, status, photo_url, reported_by.
  • claims: ID, item_id, claimant_id, proof_details, proof_photo_url, status, recipient_roll_number.
  • notifications: Real-time user alerts for claims, approvals, and returns.
  • audit_logs: Immutable trail of actions, timestamps, and performers.
  • telegram_sessions: Multi-step conversational state machine cache.

Stored Procedures & Triggers

  • is_admin(): Security-definer function returning boolean based on auth.uid().
  • handle_updated_at(): Trigger automatically refreshing updated_at timestamps.
  • publish_item_from_bot(): Elevated stored procedure allowing the Telegram bot to insert notices safely.
  • link_telegram_account(): Atomically binds a Telegram chat ID to a verified student UUID.
  • 14 Strategic B-Tree Indexes: Fast lookup on category, status, and claimant IDs.
Phase 3: Database Security

Row-Level Security (RLS) Policies

Defense-in-depth security model implemented at the database engine level

Table Operation Target Role Security Policy Rule (SQL)
profiles UPDATE authenticated auth.uid() = id AND role = (SELECT role FROM profiles WHERE id = auth.uid())
items SELECT authenticated status IN ('active', 'claimed', 'returned') OR public.is_admin()
items DELETE authenticated public.is_admin() -- Only admins authorized to delete
claims SELECT authenticated claimant_id = auth.uid() OR public.is_admin() OR reporter
audit_logs ALL authenticated SELECT only for is_admin(); UPDATE & DELETE permanently revoked
storage.objects SELECT authenticated bucket_id = 'claim-evidence' AND (is_admin() OR auth.uid()::text = folder)
Privilege Escalation Prevention: Even if a user executes direct REST calls, PostgreSQL rejects unauthorized column mutations.

Phase 3: Behavioral Modeling

UML Behavioral Modeling

State transitions and sequence flows governing item lifecycles

Item Lifecycle State Machine

[ * ] ➔ Active (Reported by student) ➔ Claimed (Admin approves claim; other claims auto-rejected) ➔ Returned (Physical ID verified at desk) ➔ [ * ]
Alternate path: Active ➔ Archived (Admin cleans up duplicate/expired report) ➔ [ * ]

Claim Lifecycle State Machine

[ * ] ➔ Pending Review ➔ Approved ➔ Awaiting Handover ➔ Returned (Recipient Roll No logged)
Rejection path: Pending Review ➔ Rejected (Admin reason sent to student via in-app notification)

Physical Handover Sequence Protocol

1. Student brings physical college ID to Security Desk ➔ 2. Admin opens /admin/handovers ➔ 3. Admin verifies Name & Roll No. on card ➔ 4. System atomically closes claim and writes immutable audit entry ➔ 5. In-app & Telegram alert sent.

Phase 4: Implementation Walkthrough

Closed Campus Wall & Institutional Auth

Eliminating public scraping and ensuring 100% verified campus identities

Mandatory Institutional Login Wall

  • All routes (/, /browse, /dashboard, /report/*) are strictly protected by React route guards.
  • Unauthenticated visitors are immediately redirected to /login.
  • Navigation links (Browse, Report, Dashboard) remain completely hidden until sign-in.
  • Prevents external scrapers or non-campus personnel from viewing internal notices.

Google OAuth 2.0 Restricted to @iiita.ac.in

  • Auth provider parameters enforce hd: 'iiita.ac.in'.
  • Client-side guard rejects any personal @gmail.com or external domains.
  • Database CHECK constraint provides redundant server-side enforcement: CHECK (email LIKE '%@iiita.ac.in').
  • First-time onboarding captures Student Roll Number, Academic Batch, and Department.
Security Verification: Tested with malicious attempts to login via personal Gmail; Supabase and React both successfully reject the attempt.

Phase 4: Implementation Walkthrough

Anti-Fraud Claim Verification Protocol

Two-factor ownership verification eliminating dispute liability and fraudulent claims

Step 1: Secret Distinguishing Details

When reporting a found item, the finder records private marks (e.g. "Has a small scratch on the bottom right and an anime sticker inside the case").

Security: Stored in database but excluded from public noticeboard view.

Step 2: Claimant Proof Dossier

Claimants must independently describe matching characteristics or upload private evidence (purchase invoice, warranty card, unboxing video, or serial number).

Rate Limit: Database unique constraint prevents spamming claims.

Step 3: Administrative Dossier Review

Security desk officers inspect the claimant's private evidence against the finder's secret marks in /admin/claims before approving.

Step 4: Automated Competing Rejections

Upon approving a valid claim, the system automatically transitions competing pending claims to rejected with explanation notes delivered via notification.

Phase 4: Implementation Walkthrough

Administrative Desk & Immutable Audit

Chain-of-custody enforcement, item moderation, and tamper-proof security logging

Handover Desk (/admin/handovers)

Physical collection modal requires desk officer to physically inspect the student's college ID card and log the recipient's verified Name and Roll Number.

Admin Deletion Authority

Admins can permanently delete duplicate or inappropriate notices from /admin/lost, /admin/found, or item detail pages with safety confirm dialogs.

Immutable Audit Trail (/admin/audit-log)

PostgreSQL table logging every action (approvals, rejections, handovers, deletions) with timestamps, admin ID, and JSON payloads. Cannot be edited or deleted.

Dispute Protection: If an ownership dispute arises later, the exact handover timestamp, verifying admin, and recipient roll number are cryptographically traceable in the audit log.
